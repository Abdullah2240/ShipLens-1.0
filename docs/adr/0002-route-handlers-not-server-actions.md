# 0002 Route handlers under /api/v1 through one route() wrapper, no Server Actions

- Status: Accepted
- Date: 2026-10-28

## Context

Next.js offers two ways to change data: Server Actions (functions called from forms and components through a framework-generated endpoint) and route handlers (plain HTTP endpoints). The judges score roles, permissions and OWASP security, and the brief asks for API documentation. Both need a real, stable HTTP contract: a permission test must be able to call every endpoint as every role, and the API document must list methods, paths, bodies and status codes.

Every mutation must also pass the same checks in the same order: who is calling, may they do this, is the request from our own origin, is the input valid. Repeating those checks by hand in each endpoint is how one gets missed.

## Decision

- Every state-changing operation is a route handler under `/api/v1`. Server Actions are not used for mutations. Server Components read data by calling services directly.
- Every handler is built with one wrapper, `route(opts, handler)`. In order, it:
  1. assigns a request id (accepts a well-formed `x-request-id`, otherwise generates one);
  2. rejects a mutating request whose `Origin` header is not exactly `APP_ORIGIN` (403);
  3. parses the query string with Zod;
  4. resolves the session from the cookie when `auth: 'session'` (401 if missing);
  5. calls `authorize(actor, action)` when an action is named and passes the resulting `Scope` on (403 if the role lacks the action, see ADR [0005](./0005-permission-table-as-data-and-scopes.md));
  6. checks the content type, caps the body at 64 KiB and parses it with a strict Zod schema (422 with field codes);
  7. builds the `CommandContext` (actor, request id, clock, pool) for `command()`;
  8. maps every error to one shape, `{ error: { code, message, details?, requestId } }`, logs denials and 500s through the redacting logger, and sets `Cache-Control: no-store` and `X-Request-Id`.
- Layering is route handler, then service (framework-free), then repository, then Postgres. ESLint `no-restricted-imports` stops services and repositories from importing `next`, `next-intl` or `react`, and stops pages and routes from importing repositories.
- `route()` lives in `src/platform/http/route.ts`. Routes written before it existed import an interim adapter with the identical call shape; switching is one import line per route, and the adapter is then deleted.

## Consequences

### Positive

- An explicit API contract: every endpoint is a file under `src/app/api/v1`, so documentation and tests can enumerate them.
- The role by action matrix test and the cross-branch isolation tests call the real handlers over HTTP semantics, proving least privilege at the edge and not only in the service.
- CSRF defence in depth: `SameSite=Lax` cookie plus an exact Origin match on every mutation.
- One error shape for the UI to translate, and one place to change behaviour for every endpoint.

### Negative

- More boilerplate than Server Actions: each mutation needs a route file, a client `fetch` and a Zod schema.
- Forms need client code to call the API; progressive enhancement without JavaScript is not available for mutations.

### Neutral

- `route.ts` is the one platform file allowed to import a module (`@/modules/auth`, to resolve the session).
- The client IP is the first `x-forwarded-for` entry, as supplied by the platform proxy; rate limits use the same rule.

## Alternatives considered

- **Server Actions.** Less code, but the endpoint is generated by the framework, which makes a documented API and direct HTTP permission tests harder. The service layer would be the same either way.
- **A checklist of checks per handler, no wrapper.** Relies on every author remembering every step.
- **tRPC or GraphQL.** A second protocol to document for no benefit at this size.
